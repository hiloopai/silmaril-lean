# C aggregate layout: bit-fields under two policies, compared with compilers

`Silmaril.Data.Layout` lays out C structs and unions for five System V and ILP32 data models,
and rejects bit-fields. `Silmaril.Data.Layout.Bitfield` places aggregates **with** bit-fields at
bit granularity under a **bit-field policy**:

| policy | source of the rule | rule (module doc) |
|---|---|---|
| `sysv` | System V AMD64 psABI §3.1.2 "Bit-Fields" (x86-psABIs/x86-64-ABI@e1ce098331da5dbd66e1ffc74162380bcc213236), with GCC 13.3's choices where the psABI leaves the rule to the implementation (unnamed and zero-width bit-fields) | a bit-field stays in the storage unit of its declared type that holds the current bit, otherwise it moves to the next aligned unit; zero-width aligns; only named bit-fields add alignment; types share units |
| `ms` | Microsoft's bit-field allocation **as clang 18.1 emulates it** for `--target=x86_64-pc-windows-msvc` (`-Xclang -fdump-record-layouts`). This is **clang's MSVC-compatible layout, not `cl.exe`**: no table here comes from Microsoft's compiler | one storage unit per declared type; a new unit when the type size changes or the field does not fit; zero-width closes the unit; every bit-field type aligns a struct; in a union a bit-field covers its unit and adds no alignment |

The other System V psABIs (i386, AArch64 AAPCS64, RISC-V) are described as using the same policy,
but **no measurement here checks them**; only x86-64 is compared with a compiler.

`msX64` is a **data model** (LLP64: `long` is 4 bytes, `long double` 8, `wchar_t` an unsigned
2-byte type) and, with `BitPolicy.ms`, a layout policy. It is **not a calling convention**: argument
passing, return values and the register discipline of Microsoft x64 are
`Silmaril.Machine.Abi.Win64`, and are not in this module.

**Proved** (standard axioms):
- `bitLayout_wf`: every slot lies inside the record, and a struct's slots are pairwise disjoint and
  in increasing order. This is a **structural** property of the placement function. It says
  nothing about what any compiler does.
- `bitfieldLayout`: the previously open `Task.bitfieldLayout`.
- `msX64_wf`: the data model's scalar shapes are well formed.
- `Examples.cases_agree`: on the **25 aggregates** of `examples/layout/cases.h`, the layout agrees
  with gcc 13.3 (System V x86-64) and with clang 18.1's MSVC emulation on every reported size,
  alignment, bit offset and width. This is **agreement on a finite sample**, regenerated by
  `examples/layout/measure.sh`, **not a proof that either policy is the ABI** for all aggregates.
- Named examples of `sizeof`, `_Alignof`, `offsetof`, physical placement and padding, including
  cases where the policies differ.

**Queries** (and what they are):

| query | meaning |
|---|---|
| `bitShapeOf` | `sizeof` and `_Alignof` |
| `offsetOf` | **C's `offsetof`**: the byte offset of an **ordinary** member. **Every bit-field is refused**, wherever it lies, also `unsigned x : 8` at offset 0 (`Examples.byteBitfield_offsetof`): `offsetof` of a bit-field is undefined (C17 7.19p3) |
| `bitOffsetOf` | **physical placement**, not a C expression: the bit offset and bit width of any named member, bit-fields included |
| `paddingBits` | the bits of the object representation (`8 * sizeof` bits) that **no named member** covers: alignment gaps, tail padding, unused bits of bit-field storage units, the bits of **unnamed** bit-fields (not members, C17 6.7.2.1p12) and, in a union, the bits beyond every member |
| `paddingBytes` | the bytes **all eight** of whose bits are padding bits. A byte holding part of a bit-field is never a padding byte; its free bits count only in `paddingBits` |

**Refused rather than approximated:**
- a bit-field wider than its type;
- a named zero-width bit-field;
- a bit-field that is not an integer, `_Bool` or enum;
- `_Alignas` on a bit-field;
- aggregates nested inside a declaration that themselves contain bit-fields (`layoutTy` refuses them);
- `#pragma pack`, `packed`, `ms_struct`.

**From a header.** `Silmaril.Data.Layout.Header.read` reads tagged struct, union and enum
definitions (members with arrays of literal size, bit-fields, `_Alignas(n)`) into `Header.env`;
`Header.Thms` lays out a parsed struct with `char`, bit-field, `long`, `int` and `double`
members under `sysv`/`sysvX86_64` (`sizeof` 32, bit-fields at bits 8 and 11, `long` 8 bytes at
8) and `ms`/`msX64` (`sizeof` 24, bit-fields at bits 32 and 35, `long` 4 bytes at 8), and a
bit-field-free one with `tagLayout`. What the reader cannot express (untagged definitions,
flexible arrays, `#pragma pack`, …) is refused, so no layout is computed for it.

**Not claimed:**
- that clang's MSVC emulation is `cl.exe`'s layout;
- layouts for other compilers, flags or psABIs than those measured;
- that the policies match their ABIs beyond the 25 measured cases;
- any calling-convention property.
