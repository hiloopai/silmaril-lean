# The logic graph

Silmaril's institutions and the maps between them, as project records that Lean checks, exported
to the project database and drawn by the explorer (`#/logic-graph`). This is the registry of
*this* repository. It is not Hets's logic graph: how the two relate is recorded per record and
shown on the Coverage page.

## What is registered

Five record kinds (`Silmaril/Project/Registry/Institution/Defs.lean`), each naming a Lean
declaration whose type Lean checks when the record is elaborated:

| kind | declaration | level | direction of `A → B` |
|---|---|---|---|
| `institution` | `Silmaril.Logic.Institution.Inst` (or a family `∀ x⃗, Inst`) | node | — |
| `comorphism` | `Inst.CoHom A B` | institution edge | signatures `Φ : Sign_A ⥤ Sign_B`; sentences forwards `Sen_A Σ → Sen_B (Φ Σ)`; models backwards `Mod_B (Φ Σ) → Mod_A Σ` |
| `morphism` | `Inst.Hom A B` | institution edge | signatures `Φ : Sign_A ⥤ Sign_B`; sentences backwards `Sen_B (Φ Σ) → Sen_A Σ`; models forwards `Mod_A Σ → Mod_B (Φ Σ)` |
| `room` | `Silmaril.Logic.Institution.Room` (or a family) | node, one level down | — |
| `corridor` | `Corridor R₁ R₂` | room edge | sentences forwards, models backwards |

Definitions and sources: rooms and corridors, Mossakowski, Diaconescu and Tarlecki 2009 §3
(`mossakowski-diaconescu-tarlecki-2009-logic-translation`); institution morphisms, Goguen and
Burstall 1992 Definition 13 (`goguen-burstall-1992`); comorphisms, Goguen and Roşu 2002
Definition 4.2 (`goguen-rosu-2002-institution-morphisms`). Every edge is drawn from `A` to `B` as
its Lean type is written; the table above says what travels which way.

**Endpoints are found by Lean.** A comorphism's record does not say which institutions it
connects: Lean reads `A` and `B` off the declaration's type and finds the registered institutions
they are (instances of), first up to reducible unfolding, then by default unfolding. An endpoint
that is not registered, or that two records name, is an error. `(from := …)` and `(to := …)` may
be given; Lean then checks them. Rooms are matched the same way, and a room that is `A.I.obj S`
for a registered institution `A` records `A` and the signature `S` (it is a *fiber* of `A`).

**Families.** A declaration with parameters (`PL.room : Type → Room`,
`PLtoFOL.corridor : (P : Type) → …`) is registered as a family: `arity` and `params` record its
binders, and an edge's endpoints record the arguments at which they are reached (`from_at`,
`to_at`). A room problem (`silmaril problem N in R`) needs a closed room.

**Facts.** `(facts := [thm, …])` lists theorems about an edge. Lean checks that each states a
known property *of that declaration*, and records the theorem's axioms (`sil project check`
rejects non-standard ones):

| property | statement |
|---|---|
| `model_expansive` (comorphism) | `Inst.CoHom.ModelExpansive f`: every model translation is surjective, so consequence is borrowed |
| `sound` (morphism) | `Inst.Hom.Sound f` |
| `model_expansive` (corridor) | `Corridor.ModelExpansive c` |

A property that is not listed is not claimed.

**Hets.** `(hets := "Name") (hets_relation := r)` relates a record to a logic or comorphism of
the Hets logic graph: `corresponds` (the same logic or translation, as far as the Lean definition
goes), `fragment` or `related` (comparable, not the same). The names are checked against
`silmaril/logic-graph/hets.toml`, the 39 logics and 75 comorphisms Hets registers at
[spechub/Hets@65ca27f4](https://github.com/spechub/Hets/tree/65ca27f4fcafd57f94fbb0908f2d88a16b0977ea)
(`Comorphisms/LogicList.hs`, `Comorphisms/LogicGraph.hs`), generated by
`scripts/logic-graph/hets_list.py`. Only names are copied; Hets is GPL-2.0 and none of its code is
included. Hets lists no institution morphisms.

## Coverage

Five questions, kept apart (explorer: `#/logic-coverage`):

1. **What does the registry omit from this repository?** `silmaril logic_audit (prefix := "Silmaril")`
   (in `Silmaril.LogicGraph.Audit.Defs`) records every non-theorem declaration reachable from that
   module whose type, after its binders, is an institution, comorphism, morphism, room or corridor,
   with its arity, module, layer (`header`, `proofs`, `raw`) and the record that registers it.
   The `logic_coverage` view counts them.
2. **How does the registry relate to Hets?** The `hets_coverage` view: per Hets logic and
   comorphism, the records that claim a relation to it, and which relation.
3. **What is each entry of the curated catalogue the registry was ported from?**
   `silmaril/logic-graph/catalogue.toml` (`logic_catalogue`, loaded by
   `Silmaril.LogicGraph.Catalogue.Defs`) has one record per entry of that catalogue (137 logics,
   158 maps), with its stable id and label, its status, the registered records that hold it, the
   Lean declarations that are its evidence and a reason when it is not a registered record:
   - `registered`: a registered record (its evidence declaration, or a named bundle of it);
   - `represented`: an instance or an endpoint of registered records (a node of a registered
     family, the source of registered comorphisms);
   - `not-institution-typed`: the evidence is a logical system (Metamath axiom sets, inference
     systems, `LogicalSystem`s), a translation of proofs, a family of institutions (a logic graph
     or a functor into institutions) or theorems, outside the five registry kinds;
   - `prospective`: the catalogue entry has no Lean declaration.
   Lean checks that every evidence declaration exists and every named record is registered;
   `sil project check` checks the status against the records, the evidence and the reason.
4. **What does the graph leave out, and why?** `silmaril/logic-graph/exclusions.toml`
   (`logic_exclusion`): every audited declaration of an institution-graph type that no record can
   hold, with its exact reason (Lean checks that it exists and is not registered); the modules not
   in this repository because they read fixtures generated by external tools (the K framework,
   egg); and the parts of the source developments outside the institution graph (solver bindings
   and proof replay of the SMT development, the rest of the type-theory development), with counts.
5. **Which logic families are not in this repository yet?** `silmaril/logic-graph/pending.toml`
   (`logic_pending`): families with Lean developments that are being contributed in reviewed
   batches. Nothing in them is registered or claimed until it lands.

## Consequence systems

A logic's consequence systems are `consequence_system` records
([consequence-systems.md](consequence-systems.md)) placed over a registered room:
`(room := R) (room_at := "a …")` says which room's sentences the system relates, and
`(reading := semantic)` or `(reading := derivability)` which kind it is. Lean checks the sentences,
and that a semantic reading *is* the room's consequence (`roomSeq R`, or `roomTheorySeq R T` over
the models of a theory `T`). `Silmaril.LogicGraph.Consequence.Defs` registers these:

| logic | derivability | semantic consequence | room |
|---|---|---|---|
| PA (`peano.mm`) | `logic.consequence.metamath.pa.derives` | `….pa.entails` | Metamath, at `pa` |
| ZF, ZFC (set.mm's set-theory fragment) | `….zf.derives`, `….zfc.derives` | `….zf.entails`, `….zfc.entails` | Metamath, at `zf` |
| Metamath over set.mm's grammar; set.mm's ZFC | `….set_mm.derives`, `….set_mm.zfc.derives` | `….set_mm.entails`, `….set_mm.zfc.entails` | Metamath, at `setMM` |
| HOL, between sequents | `logic.consequence.hol.sequent.derives` | `….hol.sequent.entails` | HOL, at the initial signature |
| HOL, on propositions | `logic.consequence.hol.kernel` | `logic.consequence.hol.seq` | none: propositions are not the room's sentences |
| extensional MLTT | `logic.consequence.mltt.extensional.derives` | `….extensional.entails` | extensional MLTT (sentences lifted by `ULift`) |
| intensional MLTT (original rules) | `logic.consequence.mltt.intensional.derives` | `….intensional.entails` | intensional MLTT, at `⊤` |

**The coverage matrix** (`Silmaril.LogicGraph.Consequence.Matrix.Defs`, registered as the evidence
matrix `logic.consequence.coverage`) sets every family (HOL, extensional and intensional MLTT, λΠ,
Metamath, PA, ZF, ZFC) against every feature. The features are abstract syntax, institution,
derivability, semantic consequence, soundness, identity/weakening/cut, substitution, completeness,
concrete syntax, concrete institution, concrete consequence systems and registration here. Each
cell names its Lean declarations, and Lean checks that they exist. A cell is `defined`, `proved`,
`registered`, `absent` or `not claimed`, and every absent cell says why. Completeness is
`not claimed` for every family. The explorer shows the matrix at the end of `#/logic-consequence/`.

The relations between them are standard consequence problems answered by the library's theorems:
`sound_at` from each derivability to its semantic consequence (soundness), from ZF to ZFC (an
inclusion), and `tarski_closed` (identity, weakening and cut). No completeness is claimed. The
library side is in [consequence.md](consequence.md) (Theories, Metamath, MLTT).

## Where the records are

The registrations are a view, `Silmaril/LogicGraph/` (one module per region of the library, and
the audit), imported by nothing but the project dump (`silmaril.toml`). A new institution is
registered next to its region's others:

```lean
silmaril institution logic.pl := Silmaril.Logic.Institution.Examples.PL.inst
  (hets := "Propositional") (hets_relation := corresponds)
silmaril comorphism logic.pl_fol := Silmaril.Logic.Institution.Examples.plToFol
  (facts := [Silmaril.Logic.Institution.Examples.plToFol_modelExpansive])
```

## Database and explorer

Tables `institutions`, `comorphisms`, `morphisms`, `rooms`, `corridors` (edge endpoints in the
columns `src`, `dst`), `logic_facts`, `logic_edge_kinds`, `logic_audit`, `hets_logics`,
`hets_comorphisms`, `logic_pending`; views `logic_edges`, `logic_nodes`, `logic_coverage`,
`hets_coverage`.

Explorer routes: **Logics** in the navigation opens `#/logics/` (every node and edge as a table,
searchable and sortable: the default view; `#/logic-table/` is the same view). **Table** and
**Graph** are tabs over the same data, and the search text goes from one to the other.
`#/logic-graph/` is the graph (level, edge-kind, search and isolated-node filters, layout, fit,
zoom, reset); `#/logic-graph/<kind>:<name>` selects and centres one node or edge, and the filters
are kept in the URL. `#/institutions`, `#/comorphisms`, `#/morphisms`, `#/rooms`, `#/corridors`
are the registries; `#/<kind>/<name>` is one record (its source, endpoints, incoming and outgoing
edges, parallel and opposite edges, facts, fibers and Hets relation); `#/logic-coverage/` is the
coverage. `#/logic-consequence/` lists the consequence systems of the logics, their rooms and
readings, and the proved relations between them; a room's and an institution's pages list theirs.
Source views read a declaration from its own module at the range Lean recorded
(`decl_locations`), whichever module registers it.

## Checking it

```
lake build Silmaril.LogicGraph.Audit.Defs     # Lean checks every record
make project-check pages                       # dump, check, database, explorer
node tools/silmaril-project/tests/explore/logic.mjs _site   # the browser walkthrough
```

**Records files are tracked inputs.** `silmaril load` reads `silmaril/logic-graph/*.toml` while
its module elaborates. The two loaders (`Silmaril.LogicGraph.Hets.Defs`,
`Silmaril.LogicGraph.Catalogue.Defs`) form the library `SilmarilLogicGraphData`, whose `needs`
names the Lake input `logicGraphRecords` (every `*.toml` there): editing a records file rebuilds
its loader and the modules importing it, incrementally, with no clean build.
`make logic-graph-check` (part of `make check`) is the regression test: it adds a probe record,
checks that the loader is rebuilt and that the record is in the loaded environment, then removes it
and checks again.
